# Implement Issue

Turn one `ready-for-agent` issue into a reviewed pull request. Headless by default: the factory's implement job runs `/harness:coding` with "route to implement-issue" and the issue number. There the workflow owns the branch claim, every status label, the merge gate, and the hand-off; you own the code, the tests, the PR text, and three marker files in `.factory/` (excluded from git) that tell the workflow how you ended: `done`, `handoff`, `split`. A local session told to work an issue end to end follows the same steps and does the workflow's parts itself (see the last section).

The issue is the whole specification. Cloud runs never see `thoughts/`, plans, or handoffs. If the issue is not self-contained, stop at step 1 with a `handoff` that says what is missing.

## Steps

1. **Read the issue and every comment**, the triage comment first: it names the root cause, the definition of done, and the test that should prove it. Write a five-line plan (what changes, where, the test, what stays untouched, how you will verify) and a numbered acceptance list in `.factory/plan.md`; they become the PR body.
   **Size check** (fresh branches only; a resumed branch is already sized). If the plan touches more than about eight files or more than one module, do not start. If auto-merge is allowed and this issue is not itself a part (its body has no `<!-- factory-part-of: n -->`): split it into two to five parts in the order they must land, each a self-contained issue one run can finish and merge. Create each with `gh issue create --label wait --title ... --body-file -`; the body gives the change, where it goes, the definition of done, the test, `Part k of m of #<n>`, and `<!-- factory-part-of: <n> -->` as its last line. Write the part numbers, one per line, to `.factory/split` and stop. If auto-merge is not allowed, or this is already a part, write the size and the proposed parts to `.factory/handoff` and stop.
2. **Orient on the branch.** You are on `claude/issue-<n>`. If it already has commits past the default branch, an earlier attempt made them: read `git log <default>..HEAD`, the diff, the draft PR, and the issue comments, then continue from where it stopped.
3. **Implement under the tdd rules.** Read `../tdd/tdd.md` (relative to this skill directory; you are the controller and can resolve it) and apply its core rules: failing test first, minimal change, no speculative generality. Conservative coverage: the regression test the triage comment asked for, plus what the change makes essential. Commit in small steps with messages that name the behavior and push after each commit (`git push -u origin HEAD`); an attempt can be cut off at any point, and your pushes are what CI runs on. After the first real commit open the draft PR (`gh pr create --draft --base <default> --head claude/issue-<n> --title <one line> --body "Closes #<n>. Work in progress."`) so the work is visible early.
4. **Run the repo's checks.** Whatever the repo declares (`package.json` scripts, `Makefile`, `pyproject`, CI config): the test command, then the lint command. Fix what fails. If a check cannot run on this runner (another OS, a missing toolchain), say so in the PR body; the PR's own CI decides at the gate.
5. **Review before finishing.** Read `../requesting-code-review/code-reviewer.md`, fill its placeholders (description = the plan; requirements = the issue and triage comment; base = the default branch SHA; head = current SHA), and dispatch it with the Agent tool on `opus`, in the foreground. Fix every Critical and Important finding, re-run the checks, commit and push. Minor findings go in the PR body. The workflow runs a second, independent review as the merge gate; the cleaner the branch you leave, the more often that gate passes.
6. **Finish the PR and mark done.** `gh pr edit <pr> --title ... --body-file -`: title is the change in one line; body is `Closes #<n>`, the five-line plan, the acceptance list with each item checked or explained, a "Review" section with the reviewer's summary and what was fixed, and how the checks were run. Then `touch .factory/done` and stop. Do not merge, do not change labels, do not mention anyone: the workflow merges when the gate passes and otherwise hands the issue to a human with the reason.
7. **Blockers.** Never touch secrets, auth, billing, payments, or migrations. If the work turns out to need them, or needs a design decision the issue does not settle, write one sentence to `.factory/handoff` saying what and why, push what you have, and stop.
8. **Never background anything.** A headless session ends the moment you end your turn, and everything you backgrounded dies with it: tests, builds, and the review subagent run in the foreground.
9. **Never push to the default branch directly.**

**Attempts.** The factory gives an issue up to four attempts in one job, each capped at 120 turns or 45 minutes; between attempts the workflow commits anything you left uncommitted and starts the next attempt only if the branch moved and no marker file exists. When the prompt says FINAL ATTEMPT, start no new work: if auto-merge is allowed and this is not a part, make the branch a coherent change whose checks pass, change the PR body's `Closes #<n>` to `Part of #<n>`, mark `done`, and list the remaining work in the PR body; the workflow merges it and you create parts for the rest as in step 1. Otherwise write the one question that blocks finishing to `.factory/handoff`.

## In a local session

Do the workflow's parts yourself, with the same meaning. Claim: branch `claude/issue-<n>` from the default branch, push it, and set exactly one status label (`gh issue edit <n> --remove-label ready-for-agent,ready-for-human,needs-info,wait --add-label in-progress`). Instead of marker files: on `done`, review the merge-gate conditions yourself (clean review, green checks on the head SHA, owner-authored issue) and merge with `gh pr ready` and `gh pr merge --squash --delete-branch`, then remove `in-progress`; on `handoff`, set `ready-for-human` as the only status label and comment with the reason; on `split`, set the parent to `wait` and work the parts in order.

## Report

Final message: the PR URL, the acceptance list with results, the reviewer's Critical/Important count before and after fixes, and any check that could not run.
