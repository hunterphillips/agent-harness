# Implement Issue

Turn one `ready-for-agent` issue into a reviewed PR, merged when the owner asked for the work and the review and checks pass, without a human in the loop. Headless by default (the factory's implement job runs `/harness:coding` with "route to implement-issue" and the issue number); a local session can run it the same way when told to work an issue end to end.

The issue is the whole specification. Cloud runs never see `thoughts/`, plans, or handoffs. If the issue is not self-contained, stop at step 2 and say what is missing.

## Steps

1. **Back-pressure.** `gh pr list --state open --json headRefName --jq '[.[] | select(.headRefName | startswith("claude/"))] | length'`. If 3 or more, comment on the issue ("queue full: N open claude/ PRs; will retry when one merges") and stop.
2. **Read the issue and every comment**, the triage comment first: it names the root cause, the definition of done, and the test that should prove it. Write a five-line plan (what changes, where, the test, what stays untouched, how you will verify) and a numbered acceptance list. These become the PR body; keep them in a scratch file outside the repo (`$RUNNER_TEMP` or `/tmp`).
   **Size check** (fresh starts only: skip it when `claude/issue-<n>` already exists, since step 3 resumes that work). If the plan touches more than about eight files or more than one module, split it before claiming anything. A part (its body ends with `<!-- factory-part-of: <n> -->`) never splits again: hand it to a human with the size as the reason. To split, write two to five parts in the order they must land, each a self-contained issue that one run can finish and merge on its own. Create each with `gh issue create --label wait --title ... --body-file -`; the body gives the change, where it goes, the definition of done, the test, `Part k of m of #<n>`, and `<!-- factory-part-of: <n> -->` as its last line. Then `gh issue edit <n> --remove-label ready-for-agent,in-progress --add-label wait`, comment on #<n> with the parts in order, and stop. The factory starts part 1, starts each next part when the previous one merges, and closes #<n> after the last. In a local session, work the parts in order yourself.
3. **Claim or resume.** If `claude/issue-<n>` already exists on the remote, an earlier attempt started this work: check it out, read `git log <default>..HEAD`, the diff, the draft PR, and the issue comments, and continue from where it stopped. The factory runs one attempt per issue at a time, so an existing branch is never a live competitor. Otherwise branch `claude/issue-<n>` from the default branch and push it immediately. Then `gh issue edit <n> --add-label in-progress --remove-label ready-for-agent`. After your first real commit, open the PR as a draft right away (`gh pr create --draft --base <default> --head claude/issue-<n> --title <one line> --body "Closes #<n>. Work in progress."`) so the work is visible and CI runs on every push even if this run ends early; step 7 fills in the body.
4. **Implement under the tdd rules.** Read `../tdd/tdd.md` (relative to this skill directory; you are the controller and can resolve it) and apply its core rules: failing test first, minimal change, no speculative generality. Conservative coverage: the regression test the triage comment asked for, plus what the change makes essential. Commit in small steps with messages that name the behavior; an attempt can be cut off at any point, and only committed work is certain to carry over.
5. **Run the repo's checks.** Whatever the repo declares (`package.json` scripts, `Makefile`, `pyproject`, CI config): the test command, then the lint command. Fix what fails. If a check cannot run on this runner (another OS, a missing toolchain), say so in the PR body and don't judge the change from partial local results: the PR's own CI decides at step 8.
6. **Review before opening.** Read `../requesting-code-review/code-reviewer.md`, fill its placeholders (description = the plan; requirements = the issue and triage comment; base = the default branch SHA; head = current SHA), and dispatch it with the Agent tool on `opus`. Fix every Critical and Important finding, re-run the checks, commit. Minor findings go in the PR body.
7. **Finish the draft PR.** Update the PR opened at step 3 (`gh pr edit <pr> --title ... --body-file -`). Title: the change in one line. Body: `Closes #<n>`, the five-line plan, the acceptance list with each item checked or explained, a "Review" section with the reviewer's summary and what was fixed, and how the checks were run. Then `gh issue edit <n> --remove-label in-progress` and comment on the issue with the PR link.
8. **Merge, when allowed.** The job prompt says whether auto-merge is allowed; that line is decided by the workflow from who wrote the issue, never by you. If it is not allowed, stop here with the draft. If it is allowed, merge only when all three hold: the review left no unresolved Critical or Important findings; `gh pr checks <pr> --watch --fail-fast` passed (a repo with no checks configured counts as passing, since step 5 already ran its checks); and nothing in this run hit the stop rule in step 10. Then `gh pr ready <pr>` and `gh pr merge <pr> --squash --delete-branch`, and comment on the issue that it merged. If any condition fails, leave the draft, comment on the issue with which one, and hand it to a human (below).
9. **Never background anything in the factory.** A headless run ends the moment you end your turn, and everything you backgrounded dies with it: run tests, builds, and the code-review subagent in the foreground and wait for them.
10. **Never push to the default branch directly.** Never touch secrets, auth, billing, or migrations; if the work turns out to need them, stop, comment on the issue with why, and hand it to a human. A run that stops here never merges. If a run ends with the issue still `in-progress`, the workflow assumes it stopped early and does that bookkeeping itself.

**Attempts.** The factory gives an issue up to four attempts in one job, each capped at 120 turns or 45 minutes. After each, the workflow commits and pushes anything uncommitted and starts the next attempt only if the branch moved and the issue is still `in-progress`; an attempt that adds nothing ends the job and hands the issue to a human. When the prompt says FINAL ATTEMPT, start no new work. If auto-merge is allowed and this issue is not a part, land what's done: make the branch a coherent change whose checks pass, change the PR body's `Closes #<n>` to `Part of #<n>`, merge per step 8, then split the remaining work into parts as step 2's size check describes. Otherwise hand it to a human with the one question that blocks finishing.

**Handing to a human.** `gh issue edit <n> --remove-label in-progress,ready-for-agent --add-label ready-for-human`, so the issue carries one status label. The comment starts with an @-mention of the repo owner (`gh repo view --json owner --jq .owner.login`); the owner reads mentions and nothing else. No other comment in this workflow mentions anyone.

## Report

Final message: the PR URL, the acceptance list with results, the reviewer's Critical/Important count before and after fixes, and any check that could not run.
